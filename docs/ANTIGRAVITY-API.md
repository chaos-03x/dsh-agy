# Antigravity upstream wire facts (ANTIGRAVITY-API)

> Wire facts measured against the installed official artifact and its release feed. Community multi-account projects are LEADS, never reference objects: they imitate different products, contradict one another, and are frozen at the version they were written against. The wire format here is authoritative against what this project records (may drift as Google iterates).

## 1. Endpoints & Environments

| Environment | Base URL | Status |
|---|---|---|
| Production | `https://cloudcode-pa.googleapis.com` | Returns 429 for consumer OAuth accounts (enterprise/license use) — verified |
| Daily | `https://daily-cloudcode-pa.googleapis.com` | **Main endpoint for consumer accounts (200, verified)**; source: head of OmniRoute runtime chain |
| Daily (Sandbox) | `https://daily-cloudcode-pa.sandbox.googleapis.com` | Verified usable (fallback); source: CLIProxy/Vibeproxy practice (opencode constant comments), OmniRoute only in discovery chain |

## 3. Auth & Headers

- `Authorization: Bearer {access_token}`; `Content-Type: application/json`; streaming also sends `Accept: text/event-stream`.
- `User-Agent: antigravity/{version} {platform}` — no `/{arch}` component. `{platform}` is the UA token pool (externalized to JSON, still uncaptured from the official binary); it is a DIFFERENT vocabulary from `ClientMetadata.Platform`'s Go-style enum below. The version must stay fresh — externalized and resolved dynamically.
- `X-Goog-Api-Client`: pool `google-cloud-sdk vscode_cloudshelleditor/0.1`, `vscode/1.86.0`, `vscode/1.87.0`, `vscode/1.96.0`.
- There is **no `Client-Metadata` header** — it was removed; neither official binary contains that name. Client identity rides in the request BODY as `metadata` (`ClientMetadata`), carrying `ideType`, `ideVersion` and `platform`, each with a captured vocabulary. The older claim "only `ideType` may be sent" is VOID: the live rejection was on the VALUE `"MACOS"`, which is not a member of the `Platform` enum (`platform` takes the enum NAME, e.g. `DARWIN_ARM64`, not the UA token `darwin/arm64`). `pnpm run verify:metadata-acceptance` re-measures acceptance with the legacy body as a control.
- Dual style (antigravity vs gemini-cli) **not done**.
- **Request envelope (OmniRoute active format)**: top level `{project, requestId, model, userAgent:"antigravity", requestType:"agent", request:{contents, tools?, toolConfig:{functionCallingConfig:{mode:"VALIDATED"}}, generationConfig?, sessionId}}`. Claude models strip the trailing model turn; tool schemas are reduced to an upstream allowlist with normalized keyword values (backend rejects ANY unknown keyword AND any non-protobuf value shape; see §3.1).
- **`contents` coalescing (adjacent same-role merge, functionResponse-family aware)**: the harness emits a fragmented per-step vocabulary — prompt, runtime-context snapshot, and `<system-reminder>` injections as separate `user` messages, one message per tool result — and its own first-party serializer coalesces adjacent same-role messages at the wire boundary, so `translate.ts` runs `coalesceContents` after the 1:1 map: parallel tool results group into ONE `functionResponse`-only user turn, and adjacent text turns merge into one. `functionResponse` parts never share a turn with text — the family validator rejects a user content mixing them (measured 400 via langchainjs#11445; this channel's tolerance for the mixed shape is unmeasured) — so an fr turn stays separate from the text turns that follow it. A model turn projecting to zero parts (thoughts-only turn on the Claude path) fuses the surrounding user runs; a text placeholder would fabricate a model utterance and a structural empty turn is unmeasured here, so that fusion is pinned known behavior (issue #93). **`functionResponse` name resolution is FIFO per id**: a tool-call id is NOT unique across a conversation — it is provider-issued when present, and otherwise the harness's own assembler falls back to `call-<blockIndex>` (per message) while `parse.ts` falls back to `String(blockIndex)` (per stream, the counter restarting at 0) — so distant turns routinely answer the same id, and Google validates `name` against the call the response answers: turn 12's `job_output` result riding turn 23's `bash` name was rejected with 400 `INVALID_ARGUMENT` for the WHOLE history, permanently, because a retry replays the same history (issue #99). `translate.ts` therefore keeps every name recorded per id in document order and consumes the oldest one on each result. An id that was NEVER recorded still falls back to the raw id (the pre-fix behavior) — it is the last resort, because an id is not a function name and is a guaranteed 400 — while a DRAINED id (more results than calls, which happens when a call was dropped from the history and its result survived) answers with the LAST name recorded for it: with nothing left to pair, that guess is right whenever the repeated calls were the same tool, where the raw id is wrong every time. Two gaps are deliberately left: duplicate ids still ride the wire unchanged (nothing dedupes them, and synthesizing ids would mis-address a real call), and the thought-signature cache in `runtime/signature-cache.ts` is keyed by that same colliding id — a separately-tracked gap, not fixed here. The Gemini-path placement of `functionResponse` in a user turn is live-accepted but never captured from the official client — a community capture (lead-level) claims the official shape rides a model-role turn after the calls; unverified here.
- **generationConfig.thinkingConfig** (four shapes; the first three are level-thinking models only): **omitted** when `catalog thinking!=='level'`, or when no `reasoningEffort` is set and the purpose is not `session-title`. **`{thinkingBudget:0}`** when `GenerateOptions.purpose==='session-title'` or `reasoningEffort` is `none`/`off` — this suppresses default thinking so it cannot eat a tight `maxTokens` cap (session titles run with very small caps). **`{thinkingLevel:"low"|"medium"|"high", includeThoughts:true}`** when `reasoningEffort` is one of the three. **`{thinkingBudget:N, includeThoughts:true}`** when a per-tier budget is configured (replacing that tier's level entirely — the two never travel together, since a level alongside a budget wins and would make the number inert), or on the Claude path when a Claude budget is configured AND `max_tokens` is strictly greater than it. Example (current `gemini-3.7-flash-tiered`; future `gemini-4-flash` without `-tiered` suffix behaves identically when marked `thinking:'level'`): `{"model":"gemini-3.7-flash-tiered","request":{"generationConfig":{"thinkingConfig":{"thinkingLevel":"medium","includeThoughts":true}}}}`.
- **The omitted branch is the ADAPTIVE path and is user-reachable.** `models.ts` deliberately declares no `reasoning.defaultEffort`: the harness resolves `effective = requested ?? reasoning.defaultEffort` and gates the selector's "provider default" entry on `defaultEffort === void 0`, so declaring one both forced an effort onto every request (`thinkingConfig` always present) and deleted the only option meaning "let the model decide". Unset, the selector offers Default plus low/medium/high; Default leaves `reasoningEffort` undefined, this field is omitted, and upstream runs its own budget. Measured on `gemini-3.8-flash-tiered`: `fetchAvailableModels` reports `thinkingBudget: -1` + `minThinkingBudget: 32` for every `*-tiered` id, and omitting `thinkingConfig` answers 200 with `thoughtsTokenCount` tracking the task.
- **Explicit numeric budgets ARE accepted by this channel** (relevant to any future budget setting): the accepted interval is `[-1, 65535]` — `-2` and `65536` both answer 400 naming that range. `{thinkingBudget:-1}` (adaptive) is itself accepted, so adaptive need not be expressed by omitting the field. `0` is accepted and clearly REDUCES thinking but does **not** reliably disable it (`thoughtsTokenCount` measured 53/69/126/67 across four runs, against 112–236 for the adaptive path), so "0 = thinking off" is not a safe claim. `8192` and `32768` answer 200 with `thoughtsTokenCount` rising. `{thinkingLevel:"auto"}` → **400** `Invalid value at 'request.generation_config.thinking_config.thinking_level'`, so the level vocabulary is closed to low/medium/high. `pnpm run verify:thinking-config` re-measures all of this — and it already caught the over-broad `0` claim above.
- **`minThinkingBudget` is NOT a validation.** A budget below a model's own reported floor (e.g. `1` where the model reports `32`) answers 200, so it must never be used as a client-side clamp — clamping would refuse values the backend accepts.
- **Two claims here are CONTRADICTED by a small measurement and must not be treated as settled.** (a) The id-bound rejection above did not reproduce: `gemini-3.6-flash-high`, `gemini-3.5-flash-low`, `gemini-2.5-flash` and `claude-opus-4-6-thinking` each answered **200** for `thinkingLevel` low/medium/high (n=2 each), with `thoughtsTokenCount` still moving with the level on the id-bound Gemini ids. Our code is unaffected (it emits only for `thinking:'level'`, so id-bound ids still never carry it), but the stated reason may be wrong. (b) "Thoughts are not streamed" (§5) is too broad: a `{"thought":true,"text":...}` part WAS observed on `gemini-3.8-flash-tiered`, though the four models that claim is scoped to are not `-tiered`. Both need a dedicated `verify:*` gate before either sentence is rewritten.

### 3.1 Tool Schema Contract (verified; whack-a-mole defense)

The backend parses tool `parameters` as a strict protobuf `Schema`: unknown keys (`$schema`, `propertyNames`, `pattern`, `minLength`, ...) and invalid value shapes (`enum: [true]` → TYPE_STRING 400; `type: ["string","number"]` → Unknown name "type" 400) each fail the whole request. The sanitizer (`src/adapter/translate.ts` `sanitizeToolSchema`) enforces the full contract, not per-keyword patches:

- **Keys** — only `type, format, title, description, nullable, items, enum, default, properties, required, additionalProperties` survive.
- **Values** — `type` must be a single enum string (union arrays normalize to the first non-`null` type, `"null"` maps to `nullable`); `enum` items must be NON-EMPTY strings (non-strings and empty strings filtered — an empty item 400s `cannot be empty`, measured; an all-empty enum is omitted entirely); `properties` is a name→schema map; `items` is a nested schema; `additionalProperties` accepts a nested schema or a boolean (`false` = no extra keys; live-verified accepted by the Antigravity upstream — OmniRoute strips it only because the public Gemini API rejects it); `required` is a string array.
- **Tool names** — `functionDeclarations[].name` accepts only `[a-zA-Z0-9_]` and ≤64 chars (MCP tool names are arbitrary; sanitized, overlong/duplicate names get a sha256 tail). Builtin Gemini tool names (`google_search`, `web_search`, `search_web`, `googleSearch`) are excluded entirely (upstream treats them as native tools).
- **Tests** — `tests/adapter.test.ts` `assertUpstreamContract` recursively asserts every keyword and value shape of the sanitized output, so any future unknown key or invalid value shape fails CI before a user hits upstream; each known rejection shape is pinned as a fixture. Real-world MCP schemas (GitHub MCP `issue_write` was the trigger: boolean enum + union type) belong in the corpus to surface shapes hand-written tests miss.

### 3.2 Image Input Contract (verified via OmniRoute production traffic)

Image input rides in `contents[].parts[]` as a Gemini-style inline part; both model families share it:

- **Part shape** — `{inlineData: {mimeType, data}}` (camelCase; `data` is pure base64 with no `data:` prefix). Image media types match the harness attachment vocabulary: `image/png`, `image/jpeg`, `image/webp`, `image/gif`; non-image media types are supported for Gemini models only (see below).
- **Claude parity** — Claude-branded models use the same `streamGenerateContent` schema; the request-side contents pass through unchanged (no Claude-specific image handling). Non-image multimodal files are never sent to Claude (see below).
- **Executor filter safety** — the upstream-side parts normalization only drops empty `text`, nameless `functionCall`, and non-replayable `thought` parts; `inlineData` parts are never touched.
- **Plugin behavior — images** — user-message image blocks are resolved from the durable attachment store and pre-converted to base64 before translation (`src/adapter/adapter.ts`); a missing store or failed read hard-fails with `UNSUPPORTED_CONTENT` (terminal) instead of silently sending text-only. Tool-result-nested images are not translated.
- **Plugin behavior — non-image multimodal files (Gemini only)** — `src/adapter/multimodal.ts` also resolves DSH file-handle text for non-image files into the same `inlineData` part shape, capped per file (20MB by default, configurable in the Config tab of DSH Settings; the effective cap is env `DSH_AGY_MULTIMODAL_MAX_INLINE_MB` > stored setting > 20MB default, so a headless run can raise or lower it without the GUI). Covered formats: `.pdf` → `application/pdf` (observed live end-to-end against Antigravity with multi-page PDFs); audio `.mp3/.wav/.m4a/.aac/.ogg/.flac`, video `.mp4/.mov/.webm`, and images `.bmp/.heic/.heif` follow Gemini's documented multimodal support and are not yet live-verified. Gating is deny-by-default (`supportsMultimodalFiles`): Claude-family models always excluded (Vertex answers 500 to non-image `inlineData`), catalog models must be vision-capable, and ids unknown to the catalog are only allowed with the `gemini-` prefix. Unlike the image path, a failed, oversized, or unsupported read is a silent fallback: the original file-handle text stays in the prompt so the model can still use its file tools.
- Evidence source: OmniRoute's OPENAI→ANTIGRAVITY translator emits this exact part shape on the same endpoints (its Claude path whitelist passes contents verbatim); self-recorded fixture pending — verify once against a live account before release.

### 3.3 Claude-path `contents[]` part contract (measured)

Claude-branded models are served by an **Anthropic-backed** validator behind the same `streamGenerateContent` envelope: its errors come back in Anthropic's native shape (`{"type":"error","error":{"type":"invalid_request_error","message":"messages.N.content.M..."}}`) nested inside the Gemini-style `error.message` string. Three part shapes that the Gemini path accepts are rejected there with 400 (all live-verified; `pnpm run verify:claude-parts` re-measures every row):

| Rejected shape | Claude | Gemini | Error |
|---|---|---|---|
| empty text part (`{text:""}`) | 400 | 200 | `messages.N.content.M.text.text: Field required` |
| `functionResponse` without an id | 400 | 200 | `messages.N.content.M.tool_result.tool_use_id: Field required` |
| replayed thought (`{thought:true,text}`) | 400 | 200 | `thinking.signature: Field required`; the `skip_thought_signature_validator` sentinel is then rejected as `Invalid signature in thinking block` |

The validator addresses parts by **index within the translated request** (`messages.N.content.M`), so an error message localizes the offending part exactly — useful when diagnosing a 400 from a long history.

- **Empty text** — DSH emits trailing zero-length text blocks after a tool call; upstream's own parts normalization drops empty `text` too (§3.2), so `translate.ts` drops them for every family.
- **`tool_use_id`** — the tool-call id is always carried on `functionResponse` (`block.toolCallId`); Gemini accepts the extra field, so this is not branched per family.
- **Replayed thoughts** — a thought can only be re-signed by the model that produced it, and the functionCall sentinel is not a valid thinking signature, so a thought from another family has **no** valid form. `translate.ts` therefore drops thought parts on the Claude path only. Reachable without any exotic setup: a mid-session switch from a tiered Gemini model (the only agy models that emit `reasoning` blocks) to a Claude model replays that history.

## 5. Response Structure

- Generation response: Gemini `candidates[]` style (`parts[]`, `text`, `thought` blocks, `functionCall`), parsed SSE event by event; additional `x-antigravity-*` metadata headers (token counts etc.).
- **Stream termination: there is no `data: [DONE]` (measured 2026-10-03, `daily-cloudcode-pa`, 3/3 short streams)**: a normal stream is a sequence of `data:` lines and ends on a final chunk whose candidate carries `finishReason` — the SSE `[DONE]` convention is accepted by the parser but never observed on the wire. Consequence: stream termination MUST be keyed on EITHER `[DONE]` or a `finishReason` (never `[DONE]` alone, which would fail every live stream), and a clean EOF carrying NEITHER signal is a cut-short stream that must fail rather than yield the default `stop` (issue #85: under load, truncated replies presented as completed turns). Ordinary streams carry zero non-`data:` lines (measured 3/3); a bare `{"error":{...}}` JSON line without the `data:` prefix right before a clean close is an ERROR path, not framing — reported with a socket capture in issue #85 (not yet independently reproduced), extracted and failed loudly by `parse.ts`.
- **A stalled body carries no wire-level signal (local guard, not an upstream fact)**: streaming runs with `bodyTimeout: 0` because a reasoning pause legitimately stays silent, so a connection that stops producing bytes is indistinguishable from thinking upstream-side; `parse.ts` bounds the gap itself (`AGY_STREAM_IDLE_TIMEOUT_MS`, default 180s, any byte resets it) and abandons the read.
- **Zero-length text parts are routine (measured)**: tool-call turns and stream terminators carry `{thoughtSignature, text: ""}` parts. An empty text part is rejected on replay by the Anthropic-backed Claude path (`...text.text: Field required`), so `parse.ts` skips them (issue #77) instead of fabricating empty content blocks — without closing an open block, so text continuity survives — and `translate.ts` additionally drops empty text/thought parts for every family (defense in depth for history recorded before the parser fix).
- **A retired model id answers 200 with a plain-text retirement notice and NO `finishReason` (measured 2026-10-04)**: `gemini-3-flash-agent` returned "Gemini 3.5 Flash is no longer available. Please switch to Gemini 3.7 Flash in the latest version of Antigravity." as ordinary text and closed the stream — which the #85 completeness guard correctly reports as a cut-short stream. Discovery still lists retired ids, so a stale pick fails as a stream error rather than a clean model-not-found; verify scripts must prefer ids known live over discovery order (`verify:contents-coalescing` pins the pattern).
- **Tool-call signature (protocol requirement, verified)**: outbound `functionCall` parts must carry a sibling `thoughtSignature` (400 "Function call is missing a thought_signature in functionCall parts" otherwise); the response-side functionCall part carries that signature (`{thoughtSignature, functionCall:{id,name,args}}`), which must be captured by `functionCall.id` and replayed on the next turn; when nothing is cached the `skip_thought_signature_validator` sentinel is used (both reference implementations default to it). Parallel functionCall signature semantics: see OmniRoute openai-to-gemini.ts.
- **Thoughts are not streamed (verified)**: `usageMetadata.thoughtsTokenCount` reports the thought-token count, but all models (gemini-3.6-flash-high / gemini-3-flash-agent / claude-opus-4-6-thinking / gemini-2.5-flash-thinking, incl. explicit `thinkingConfig`) stream **no `{thought:true}` parts** — thinking is either distilled into the final `text` (3.5 Flash family writes reasoning into the answer) or fully hidden (Claude family just outputs the answer). DSH front-end therefore shows no reasoning block; parse keeps thought-part support only defensively.
- `fetchAvailableModels`: `{models: Record<id, {quotaInfo?: {remainingFraction, resetTime}, displayName, modelName}>}`; **no capability metadata** (contextLength etc. must be filled from a local catalog); non-chat models present need filtering.
- **Role lists beside `models` (verified on a live account)**: `tabModelIds`, `commandModelIds`, `imageGenerationModelIds`, `mqueryModelIds`, `webSearchModelIds`, `commitMessageModelIds`, `audioTranscriptionModelIds` (arrays of ids); `deprecatedModelIds` (an object keyed by the retired id, not an array: `{oldId: {newModelId, oldModelEnum, newModelEnum}}`); and the positive signals `defaultAgentModelId`, `agentModelSorts` (`[{displayName, groups:[{modelIds}]}]`), `tieredModelIds` (`{flash|pro|flashLite: [id]}`). Ids in the role lists follow no naming rule: `tabModelIds` carries `chat_20706`, which the `tab_` prefix test misses; `mqueryModelIds`, `webSearchModelIds` and `commitMessageModelIds` all name `gemini-3.1-flash-lite`, a pinned catalog chat model. Two ids can share a `displayName`: `gemini-3.1-pro-high` and its `newModelId` `gemini-pro-agent` are both "Gemini 3.1 Pro (High)".
- **Plugin behavior**: `mergeModelCatalog` hides the members of `tabModelIds` / `imageGenerationModelIds` / `audioTranscriptionModelIds`, and a `deprecatedModelIds` key whose `newModelId` is present, chat-callable and not role-hidden (a retired id whose replacement the account does not carry stays listed; replacement availability is judged against role hiding alone, so a chain resolves independent of key order). The utility roles (command, mquery, webSearch, commitMessage) are not consumed because they name ordinary chat models. The three positive signals veto hiding, so an upstream labelling mistake cannot remove a working model. Hiding affects `listModels` only: `resolveModel` accepts any id, and the quota views (`dsh-agy status`, the Settings → Antigravity section) still count every entry of `models`.
- Quota semantics: `fetchAvailableModels` `quotaInfo` is the source for PER-MODEL pressure (`remainingFraction` + `resetTime`, and nothing else — measured across every id, so it cannot express a window), and `loadCodeAssist` supplies the project/tier. It is NOT the only quota source, which corrects this line's earlier claim of a single source with "no retrieveUserQuota path".
- **`v1internal:retrieveUserQuotaSummary` is the only source of the 5-HOUR and WEEKLY windows (verified).** Response: `{groups:[{displayName, buckets:[{bucketId, window, remainingFraction, resetTime, displayName, description}]}]}`. Measured on a live account: groups `Gemini Models` (`gemini-5h`, `gemini-weekly`) and `Claude and GPT models` (`3p-5h`, `3p-weekly`); `window` is `5h` or `weekly`. Two facts worth keeping: the split is by GROUP, not by model, and `3p-*` covers Claude AND GPT together — no model-id prefix rule in `modelFamilyOf` reproduces it, so the grouping is carried through verbatim rather than re-derived. It answers 200 under the same bootstrap User-Agent `fetchAvailableModels` uses, so no additional impersonation is needed. `dsh-agy` persists it twice, under two intentionally different shapes. `cachedLimits` is the DISPLAY cache: per-GROUP, written by `session.refreshLimits` (exposed as the `account.limits` RPC), safe for a pool of any size — including a single account, which the scheduling refresh skips entirely. `cachedQuota` is the SCHEDULING cache: per-FAMILY (google/anthropic/openai), and the weekly window reaches it too, because `rankPoolCandidates` turns a measured `remainingFraction <= 0` or `weeklyFraction <= 0` into a `blockedUntil` and a week-exhausted account must be rotated away rather than discovered by a failed request. Both paths therefore read this endpoint. The separation that remains load-bearing is the DIRECTION: `refreshLimits` writes `cachedLimits` alone and must never touch `cachedQuota`, so a display update can never block an account.
- **Implicit-cache reporting (verified)**: `usageMetadata.cachedContentTokenCount` is not always present — only reported once the cache is warmed and the prefix is large enough (gemini family ~16k+ prefix, hits from ~3rd request; claude family warms faster, can hit on 2nd request at ~99%). Single-turn/small-prefix requests always lack the field; that does not mean the model lacks caching. Test script `scripts/probe-cache-context.mts` (all three models reproduce: gemini-3.7-flash-tiered / gemini-3-flash-agent / claude-opus-4-6-thinking).
- **Cache key = prefix content, independent of sessionId (verified)**: `scripts/probe-cache-loss.mts` uses the same 20.5k system prefix byte-for-byte as an earlier probe with a fresh sessionId and hits 20447 tokens on the first round — the cache is shared across sessions by prefix hash. DSH's 0% on a new conversation's first round is really because the system prefix ~13.5k < 16k threshold (never cached) plus differing per-conversation history, not sessionId isolation.
- **Cache writes are async, ~2 rounds behind, batched by block (verified; root of the hit-rate ceiling)**: with byte-identical prefixes (append-only construction), `cached` still lags the previous full prompt each round — the hit prefix jumps by "the previous round's added block" (verified +4086 = one fill block per round), writes lag ~2 rounds; steady-state each round misses ≈ 1.5-2x the new additions -> hit-rate ceiling ~88-92%. Contrast DeepSeek's immediate full write (each round misses only the new content -> ~99%): this is why agy's hit rate can't reach 99%; upstream behavior, not controllable.
- **generationConfig.maxOutputTokens ceilings are model-family-specific (measured)**: the Claude family rejects anything above **64000** on this channel (64000 → 200, 64001 → 400 `INVALID_ARGUMENT: Request contains an invalid argument`; deterministic across `claude-opus-4-6-thinking` / `claude-sonnet-4-6`, with and without the full 87-tool payload), while the Gemini family accepts **65536** on the same endpoint. Do **not** derive the Claude number from Anthropic's public API limits: agy may front a self-hosted or otherwise gated Claude deployment with its own capacity and validation rules, so the channel's own response is the only authority. Because `catalog.ts` `maxOutputTokens` becomes the harness-injected `defaultMaxTokens`, an over-cap value there fails **every** Claude request (the reported `session-9b7d1885` 400); `translate.ts` `AGY_CLAUDE_MAX_OUTPUT_TOKENS` clamps as a second line of defense covering explicit `maxTokens` and dynamically discovered Claude ids.
- **Two 400 texts separate a bad FIELD NAME from a bad VALUE (measured; read them before bisecting)**: an unrecognized `generationConfig` key is named explicitly — `Invalid JSON payload received. Unknown name "maxTokens" at 'request.generation_config'` — whereas a recognized key with an out-of-range value returns the generic `Request contains an invalid argument.` (`INVALID_ARGUMENT`). So a name mismatch never masquerades as a value problem: the reported `session-9b7d1885` 400 was the generic text, i.e. the field name was correct (`translate.ts` maps DSH's `options.maxTokens` → `generationConfig.maxOutputTokens`) and only the 65536 value was over the Claude ceiling.
- Error-classification inputs: HTTP status + `Retry-After` / resetTime / error JSON shape -> runtime/classify. Generic 400s are `request-error` (permanent — retrying resends the same broken payload, so no rotation); only capacity-style 400s (context overflow / model unavailable) are transient.
